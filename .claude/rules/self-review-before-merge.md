# PR は自己レビューを収束させる（self-review before merge）

## 原則

**PR を作成したら、マージ（またはレビュー依頼）に進む前に必ず自分でレビューする。「レビュー → 修正 → 再レビュー」を、Blocker / Should が出なくなるまで、かつ事前に決めたラウンド上限の範囲で反復する。**

ゴールは「マージして問題ない状態」であって「レビューアが何も言わなくなる状態」ではない。**指摘ゼロを条件にすると Nit（好み・命名・整形）でループが際限なく伸びる**ため、打ち切りは重大度で判断する。

## 手順

0. **先にラウンド上限を決める**（diff の規模と性質から。決めた値は記録する）:
   - docs / 設定のみ・新規ロジックなしの小さな diff → **1 ラウンド**
   - 通常の機能追加 / バグ修正 → **2 ラウンド**
   - 高リスク（認証・権限・課金・データ破壊・外部契約変更・複数レイヤー）→ **3 ラウンド**
1. PR 作成後、自分の diff を一度**通しで**レビューする
2. 観点（最低限）:
   - 仕様 / 依頼との整合（やるべきことをやり、やらないことをやっていないか）
   - 正確性（バグ・エッジケース）
   - テストカバレッジ
   - セキュリティ
   - **依頼に直接トレースできない不要な変更**が混ざっていないか（外科的変更）
3. レビュー**手段**は既存のものを活用してよい（`/review`・`/code-review`・`/codex` 等）。観点をここで再発明しない。ただし**毎ラウンド手段を重ねない**（1 ラウンド 1 レビューア。セカンドオピニオンは高リスク時に初回だけ）
4. **指摘を分類してから直す**:
   - **Blocker**（バグ / 仕様不整合 / セキュリティ / 受入条件のテスト欠落 / 不要変更の混入）→ 必ず直す
   - **Should**（単独ではマージを止めないが直すべき）→ そのラウンドでまとめて直す
   - **Nit**（好み・軽微な命名・整形）→ **ループ対象外**。最終ラウンドで一括修正するか、follow-up issue / PR コメントに落として明示的に見送る
   - 妥当でない指摘は直さず、**理由を記録する**（指摘を消すために実装を歪めない）
5. 修正を検証する（`~/.claude/rules/verification-before-completion.md`）。ただし**各ラウンドでは影響範囲のテストだけ**を回し、**フルテスト / E2E はループ終了後の最終ゲートで 1 回**にする
6. **2 ラウンド目以降は直前の修正差分だけ**をレビューする（全体を毎回見直さない）。3〜6 を繰り返す

## やめどき

次のいずれかを満たしたら完了する:

- **収束**: そのラウンドで**新規の Blocker / Should がゼロ**（残った Nit は上記のとおり処理）
- **上限到達**: 事前に決めたラウンド上限に達した → **残指摘を重大度つきで一覧にしてユーザーに提示し**、「直す / follow-up issue に切る / 受容する」の判断を仰いで終了する
- **堂々巡り**: 同種の指摘が 2 ラウンド連続で出た → 好みの問題とみなし、ユーザーに判断を仰いで終了する

いずれの場合も、最後に**最終ゲート（フルテスト + E2E）を 1 回**通してから完了とする。

## 禁止

- 自己レビューせずにマージ / レビュー依頼へ進む
- 指摘を認識したまま「完了」と報告する（見送るなら**見送ったと明示する**）
- 指摘対応のついでに無関係なリファクタを混ぜる（指摘対象だけ直す）
- **ラウンド上限を決めずに始める / 上限到達をユーザーに告げずに回し続ける**
- **Nit のために追加ラウンドを回す**
- **毎ラウンドでフルテスト / E2E を回す**（最終ゲートで 1 回）

## 補足

プロジェクト側により具体的なレビュー手順がある場合（例: GitHub 上にレビューコメントを付ける運用）は、そのプロジェクトの規約を優先する。本ルールは「自己レビューを指摘ゼロまでループする」という規律の最小定義。
